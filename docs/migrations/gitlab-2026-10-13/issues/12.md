## Description

## Problem

A vessel settlement writes two stores that share no transaction: the ship's side (cargo
manifest, port supply, contract, dock-fee balance) goes to MariaDB, and the captain's gold goes
to the player file. Since S11 (work item #10, MR !17), `cargobuy` and `cargosell` record the
trade first, then save the gold with `save_char_checked()`. If that save fails, they record the
pre-trade state again. If that undo cannot be recorded either, the trade stands, in memory as in
the database, and the persistence service's per-minute checked save stores the gold once the
disk recovers.

One window stays open: a failed player-file save, a failed undo, and then a crash before any
later save succeeds. The database then keeps the trade and the player file keeps the old gold,
so a buyer keeps both the gold and the cargo, and a seller loses the cargo without being paid.

A settlement record kept only in the database cannot close this window. At recovery it cannot
tell whether a later save carried the gold, so a record left behind by a failed delete would
undo a paid trade or put sold cargo back aboard (a dupe). It only moves the window to the mirror
case: the save succeeded, but the delete failed before the crash.

## Full fix

Treat each vessel settlement as two-phase, with a marker in the player file:

- A settlement table (schema phase with rollback and verifier SQL, `master_schema.sql`, the boot
  ensure function). Its row is written in the same transaction as the trade and carries the
  undo: signed deltas for the supply and the lot, not absolute values.
- A player-file field: the newest settlement id whose gold this file holds, saved with the gold.
- Reconcile at login, and before the ship's next trade or cargo save: a row the player file
  covers is settled (delete it), and a row it does not cover is undone (apply the deltas). The
  ship's trading is held while a row is open.
- "Undone" is reported only after the undo commits.

## Same shape elsewhere

Freight acceptance (`do_contractaccept`, `vessels_contracts.c`) and dock-fee payment
(`do_dockfees`, `vessels_trade.c`) also compensate after a failed save, and on a failed
compensation they only log a `SYSERR` and report that no gold was taken. They should use the same
settlement path.

### Comment 3948779792

Max aka Mosheh (max757) at 2026-10-03T07:13:58.992Z.

Two cases from MR !17's second review round (2026-10-03) belong here.

**A trade COMMIT that goes unanswered** (MariaDB client error 2013) is now settled in
`trade_record()` (fix `2ba35d6b1`, on `feat/vessels-s12` / MR !18): the trade's writes set absolute
values, so it is written again on a reconnected session, and the second commit decides the
outcome. What remains: if that second write cannot commit either (the database unreachable just
after a lost reply), the database may not match the ship's hold until her manifest is next written
and the minute save runs. A reload before then lets the database's version win. A settlement
record would close this.

**Freight acceptance** (`do_contractaccept()`, `src/vessels/vessels_contracts.c`) has the same
COMMIT shape: an unanswered COMMIT unloads the freight and reports "no gold was taken" even if the
contract was taken and the freight stowed. Its write is conditional
(`UPDATE ... WHERE status = OPEN`), so it cannot simply be repeated: writing it again after a
commit that did land finds the contract taken and reports another captain. The settlement record
planned here (a durable intent the reconcile can find) is the fix; dock-fee payment should get the
same check.
