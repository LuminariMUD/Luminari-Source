## Description

## Problem

Three places in `src/obj/act.item.c` drop memory that belongs to an object's special abilities,
or an object itself. Read from the code, not measured.

- `downgrade_item()` sets `obj->special_abilities = NULL` without freeing the list.
- `do_applyoil()` creates the new ability with `CREATE(weapon->special_abilities, ...)`. The code
  reaches that line when the weapon has no ability other than `SPECAB_NONE`, so a weapon whose
  list holds only `SPECAB_NONE` placeholder records, as some prototypes in the dev world files
  do, loses those nodes without a free.
- The preview branch of `do_downgrade()` (no confirmation code yet) makes an object with
  `read_object(ITEM_PROTOTYPE, VIRTUAL)`, copies the player's object over it with `copy_object()`,
  shows its stats and returns. The preview object is never extracted, so each preview leaves one
  object in `object_list`.

## Proposed fix

Free the list with `free_obj_special_abilities()` in the first two places, and extract the preview
object before the preview branch returns. Check first what `copy_object()` shares between the
preview object and the player's object, so that the extraction frees nothing the player's object
still uses.

Tests: `downgrade` (preview, then confirm) and `applyoil` on a weapon with placeholder records,
under the memory-check and sanitizer jobs, and a count of `object_list` before and after a
preview.

Found on 2026-10-05 while tracing the review finding of MR !23 (work item #19); it is not part of
that work.

### Comment 3958746980

Max aka Mosheh (max757) at 2026-10-05T22:20:03.160Z.

From work item #30 (MR !26), 2026-10-06. The check this item asks for, of what `copy_object()`
shares between the preview object and the player's object:

- Before !26 the copy also took the object's list, hash, holder and content links. !26 ends
  that: a target keeps its own runtime fields (`overwrite_object()` in `src/olc/genobj.c`).
- After !26 the preview object still points at the player's object's `special_abilities`,
  `sbinfo`, `script` and `proto_script`. `downgrade_item()` clears the first of them, but not
  when it returns early.
- The copy also gives the preview object the player's object's `item_number`, while it stays on
  the hash chain and in the instance count of the prototype it was read from.
  `remove_obj_from_rnum_hash()` and the count in `extract_obj()` go by `item_number`, so the
  preview object cannot simply be extracted as it is.

One thing waits on this item. An OLC save of a prototype (`add_object()`) still drops the
special abilities, spellbook and script each live object held, without a free. !26 left that
alone because the preview object, and an open iedit copy of a spellbook, can point at the same
lists, and freeing them at the save could free one list twice. Once no two objects share a
list, `free_all_object_strings()` can free them too.

### Comment 3969817771

Max aka Mosheh (max757) at 2026-10-07T11:11:34.741Z.

Update from MR !26, merged on 2026-10-07 as `632b50242`. It changes two points of the note above.

What the preview copy shares with the player's object now:

- Its own `script`: `overwrite_object()` keeps the target's script (`dd9732777`).
- Its own `item_number`: a live target keeps its rnum, so the preview object stays a consistent
  instance of `ITEM_PROTOTYPE` on that prototype's hash chain and count, and `extract_obj()` can
  take it out as it is.
- Still shared: `special_abilities`, `sbinfo` and `proto_script`. `free_obj()` frees all three
  with the preview object, so extracting it still frees lists the player's object uses. The
  read_object() copies of the carrier's own lists that the copy replaced are lost.

What an OLC save does now (`follow_prototype()` in `src/olc/genobj.c`; `free_all_object_strings()`
is gone):

- It no longer touches a live object's script or trigger list. The save loop extracts the script
  and frees the list.
- A live object keeps an ability list or spellbook of its own. One that still matched the old
  prototype is replaced by a copy of the new prototype's and given up, not freed, because this
  preview copy and an open iedit copy (spellbook) can point at it. That is the one point still
  waiting on this item: once no two objects share these lists, `follow_prototype()` can free the
  replaced ones.
