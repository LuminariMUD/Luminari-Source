## Description

## Problem

`cargobuy` and `cargosell` (`src/vessels/vessels_trade.c`) move gold only in memory, then write the cargo manifest and the port's supply to the database. Neither saves the player file, and `vessel_db_save_cargo()`'s result is not checked.

- **Buying:** `award_gold(ch, -cost)`, then `port_adjust_supply()` and `vessel_db_save_cargo()`. If the server crashes before the captain's next routine save, the cargo is in the database but the gold comes back on reload: free cargo.
- **Selling:** `award_gold(ch, revenue)`, then the supply and manifest writes. A crash before the next save loses the sale's gold while the cargo is already gone. If the manifest write fails, a later save keeps the gold with the cargo still recorded aboard: sold cargo that can be sold again.

## Background

This is the same gap MR !15's review found in freight contract acceptance ([P2], note 3943254722). That was fixed there in `a703572e3`:

- the contract claim and the manifest commit in one transaction;
- the bond is debited only after that commits, then saved with `save_char_checked()`;
- a failed save restores the gold, reopens the contract and unloads the freight;
- `vessel_db_save_cargo()` now returns whether its writes succeeded.

`cargobuy` and `cargosell` predate S9 and were left out of that fix to keep it to the finding.

## Fix

Give both commands the same shape:

- write the manifest and port supply in one transaction;
- move the gold only after it commits, and save it with `save_char_checked()`;
- on a failed save, restore the gold and undo the manifest and supply changes.

Add DB-backed tests for a refused manifest write and a failed character save, like `Test_vessel_freight_bond_pays_for_the_goods`. New SQL that carries values must use `PREPARED_STMT`, since `check_sql_interpolation.py` gates the file's count.
