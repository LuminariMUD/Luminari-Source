## Description

## Problem

Every MariaDB connection is created with `MYSQL_OPT_RECONNECT` on (`src/database/mysql.c:174`,
`322`, `466`, `554`). A probe against MariaDB (2026-10-03, while fixing MR !17's second review
finding) showed what this does to an open transaction when the connection drops:

1. The next statement fails with client error 2006. The library refuses one reconnect because the
   session was "in transaction", and clears that flag.
2. The statement after that reconnects silently and runs in **autocommit on a new session**. The
   server has already rolled back the original transaction, so earlier writes are gone while later
   ones land on their own. Even a `COMMIT` then reports success with nothing saved.
3. A `COMMIT` that fails with client error 2013 was sent, but its reply was lost, so the outcome
   is unknown. Code nearly everywhere treats that as "rolled back".

Code is safe only if it issues nothing but `ROLLBACK` after the first failed statement in a
transaction, and if it treats an unanswered `COMMIT` as unknown. Cargo trades were fixed on
`feat/vessels-s12` (`2ba35d6b1`, MR !18): `vessel_db_save_cargo()` stops at its first failure, and
`trade_record()` writes again after an unanswered COMMIT. A read-only audit of the other 25
transaction sites found these.

## Writes that continue after a failure (partial writes land outside the transaction)

- **Player object saves can duplicate items** (`src/obj/objsave.c`). The object writer returns 1
  even when its INSERT failed (561-567), and `Crash_save` ignores results from its recursive calls
  (1095-1096). The bag saves ignore their results too (1340-1349, 1477-1486, 1565-1574), as does
  the sheath writer (576, 580). So `Crash_crashsave` and `Crash_rentsave` always reach COMMIT.
  After a drop, the server rolls back the DELETE, the later INSERTs autocommit, the COMMIT
  "succeeds", and `PLR_CRASH` is cleared (1376). The next login loads the old rows plus the new
  partial ones. Periodic crash saves are a hot path (`limits.c:1405`).
- **`Crash_idlesave` never commits** (`objsave.c:1379-1502`). It opens the transaction through
  `objsave_begin_player_save()` and has only ROLLBACKs, so every later autocommit statement on
  `conn` joins that open transaction. It runs only when `free_rent` is NO; the default is YES.
- **House contents** (`src/obj/house.c:125-129`, `166`): the same always-1 writer.
- **Pet gear** (`objsave.c:1121-1126`, used by `save_char_pets` and `pet_store_pet` in
  `src/player/players.c`): the contents branch keeps writing after a sibling write failed.
- **Help import** (`src/olc/hedit.c:3599-3606`, `3364`, `3370`, `3499`): the loop counts errors and
  carries on. The final ROLLBACK reports that everything was rolled back, while a partial import
  stays in the database.
- **Help save** (`hedit.c:633-653`, `764-796`): the version-history and keyword-DELETE statements
  are unchecked, so a drop there leaves the save non-atomic, and the COMMIT can report success.
- **Bounty overwrite** (`src/vessels/vessels_merchants.c:783` -> `vessels_piracy.c:617-626`,
  `657`): a failed bounty read inside the transaction returns 0. Then `0 + amount` is written as
  the absolute bounty on the reconnected session, overwriting a larger bounty downward.

## COMMITs whose outcome is unknown, treated as rolled back

- `pet_retrieve_stored` (`players.c:8112-8117`): if the commit landed, the pet row is ACTIVE with
  no live pet, and the next pet save deletes it with its gear.
- `pet_store_pet` (`players.c:7892-7897`): a STORED row plus the live pet, which means a duplicate
  pet or a key clash on later saves.
- `vessel_transfer_owner` (`src/vessels/vessels_ownership.c:219-233`): memory reverts to the old
  owner but the database keeps the new one, so ownership flips at the next reboot.
- `vessel_event_finish` (`src/vessels/vessels_events.c:712-729`): a staff retry applies the
  leaderboard increments a second time.
- `do_contractaccept` (`src/vessels/vessels_contracts.c:598`): the contract stays TAKEN with
  nothing in the hold (also noted on #12).

## Also seen in the audit (not reproduced)

- When a pooled connection fails its ping, `mysql_pool_acquire` closes and replaces it
  (`mysql.c:309-318`). That would leave the global `conn` pointing at freed memory, and the ping
  fails in exactly this in-transaction case.
- The help-sync lock (`help.c:140`, `GET_LOCK`) belongs to the session, so a silent reconnect
  drops it without the holder knowing.
- Not a transaction issue: `hedit.c:743-745` calls `mysql_store_result(conn)` after a prepared
  SELECT, so it returns NULL and removed help keywords are never deleted.

## Proposed fix

- **One rule for every transaction:** after the first failed statement, issue nothing but
  ROLLBACK. Writers inside transactions (the objsave and house writers, `Crash_save`, the bag and
  sheath saves, the pet gear branch, the help import helpers) return failure and stop. The
  bounty read propagates its failure. `Crash_idlesave` commits.
- **An unanswered COMMIT (client error 2000-2999) is unknown, not rolled back.** Where the writes
  are absolute and idempotent, write again on a reconnected session, as `trade_record()` now does.
  Where they are conditional or incremental (pet store/retrieve, owner transfer, event finish,
  freight), read back a durable marker after reconnecting before choosing a state. #12's
  settlement record covers the vessel cases.
- **Consider a shared helper** (for example `db_commit_checked()` returning
  committed/refused/unknown) so each site does not reinvent the classification.
- **Tests:** DB-backed CuTest cases per fixed site. Inject an unanswered COMMIT at the test level,
  and for a real drop use `mysql_send_query(conn, "COMMIT", 6)`, `shutdown()` of
  `mysql_get_socket(conn)`, then `mysql_read_query_result()`, which gives a real 2013 after a real
  commit. Real drops need persistent tables, because TEMPORARY fixtures vanish on reconnect.
- **The pool's stale-`conn` replacement and the help-lock loss** need their own check.

Found and spot-checked on 2026-10-03 (objsave writer, `Crash_idlesave`, bounty read confirmed in
the code); the audit is read-only and only the trade path was fault-injected.

### Comment 3949843987

Max aka Mosheh (max757) at 2026-10-03T19:24:27.461Z.

Correction to the S13 note above, which said the object and house writers keep their return values (plan commits 5e4ee1425 and 92efc3d73 on `feat/vessels-s13`, Part 5 item 13).

The query-layer rule covers the lost connection, but one case the proposed fix would have touched is not a lost connection: **a row that fails while the connection is good.** `objsave_save_obj_record_internal()` (`src/obj/objsave.c:561-567`) logs one `SYSERR` line and returns 1, and the sheath writer (`objsave.c:4694-4699`) does the same, so the save commits without that item and tells no one. S13 closes this in two parts.

**No item is unsaveable.** Two things make a row fail on a healthy database, and both go:

- **Record size.** The object and sheath writers refuse a record longer than their 36,767-byte buffer (`objsave.c:555`, `4684`). The buffer is sized to hold every bounded part of a record, and an extra description that does not fit, the only unbounded part, is left out instead of the item. The largest of the 489,375 saved player object records in the development database is 2,400 bytes.
- **The fresh-install `house_data` definition.** `sql/master_schema.sql` and `src/database/db_init.c` put a unique key on `vnum`, while the writer stores one row per object, so a house on a database created from them keeps one object. The key goes, with a migration for such databases. The live table has no such key (9,743 rows over 44 houses in the development database), and the tests shadow the table with a temporary one that has none either, which is why nothing caught it.

**A row that still fails is a database fault**, and the save says so:

- The object, sheath and house writers report the failed row.
- The save still commits everything else.
- The save counts as incomplete: `PLR_CRASH` (or `ROOM_HOUSE_CRASH` for a house) stays set, so the next pass retries it.
- The staff are told whose item it was.

The save does not fail as a whole: committing the rest loses less under a fault, and `Crash_rentsave()` removes worn gear from memory slot by slot before its `COMMIT` (`objsave.c:1546-1562`), so a rollback there would leave the previous save as the player's inventory.

With these, S13 covers everything this item lists.

What was built, against this item's list:

- **The rule is in the query layer** (`src/database/mysql.c`). A connection that lost its
  transaction is marked and refuses every statement until the caller ends the transaction, so no
  writer has to stop at its first failure. Besides a failed statement, a ping and the close of a
  prepared statement can be the first to meet the drop; both are caught.
- **`mysql_commit_transaction()`** reports committed, refused or unanswered. Pet store and
  retrieve, the owner transfer and the event finish read the database back after an unanswered
  `COMMIT`; cargo trades write again. Freight acceptance stays with #12.
- **Object and house saves**: `Crash_idlesave()` commits; a row refused on a good connection is
  left out, the rest is committed, the crash flag stays and the staff are told; an extra
  description that does not fit a record is left out instead of the object; `house_data` loses
  the unique key on `vnum`, with a boot migration.
- **Also seen in the audit**: the pool no longer closes the handle `conn` points at; the help
  writers check that their session still holds the help-sync lock; `hedit` deletes removed
  keywords; a bounty that cannot be read is not overwritten.

Found on the way and fixed in the same merge request: `mysql_pool_acquire()` could hold the game
while the database was away; `Crash_cryosave()` stored a frozen character's objects twice; and
the rule itself is limited to one game pulse, so a missed `ROLLBACK` in later code cannot leave
the connection refusing everyone's statements.

Review round 1 on MR !20 (2026-10-04) widened what S13 covers. Nine findings, all fixed on the branch:

- A deadlock's victim is marked like a lost connection (error 1213). The plan had left deadlocks out.
- A `COMMIT` whose outcome cannot be read back is no longer taken for a rollback: the vessel event's finish is idempotent on its own row, and the pet keeper chooses no state until `pets restore` has read the rows.
- The rent, idle and cryo saves are written a second time when the first did not reach the database, and take their objects out of memory either way, so nothing is dropped in the room beside a save that holds it. The cryo and idle saves write the bags.
- An incomplete object or house save sets its crash flag, so it is retried even when it was not asked for by the flag.
- Smaller: a sheath lying in a house no longer crashes the house save, `hedit` refuses to save over an entry it did not load, a plunder's bounty is announced only when recorded, and the pool query clears its result.
