## Description

`Test_pet_persistence_legacy_schema_migration_is_idempotent` (`unittests/CuTest/test_database_persistence.c:792`) fails on a database that was built from `sql/master_schema.sql` alone, when the syntax-check boot has not run against that database first. It passes in the local CI matrix and in `make test-all`, where the boot runs before it.

Seen twice: in S5's verification (2026-09-30, "passes on rerun") and by the reviewer of MR !21 (2026-10-04). Reproduced on 2026-10-04 at `b485062c8`.

## Repro

```bash
docker run -d --rm --name petprobe -e MARIADB_ROOT_PASSWORD=probe -e MARIADB_DATABASE=luminari_probe \
  -p 127.0.0.4:3306:3306 mariadb:10.11
docker exec -i petprobe mariadb -uroot -pprobe luminari_probe < sql/master_schema.sql
LUMINARI_TEST_MYSQL_ENABLE=1 LUMINARI_TEST_MYSQL_HOST=127.0.0.4 LUMINARI_TEST_MYSQL_PORT=3306 \
  LUMINARI_TEST_MYSQL_USER=root LUMINARI_TEST_MYSQL_PASSWORD=probe \
  LUMINARI_TEST_MYSQL_DATABASE=luminari_probe LUMINARI_TEST_SKIP_SYNTAX_BOOT=1 \
  CUTEST_FILTER=Test_pet_persistence_legacy_schema_migration_is_idempotent ./cutest
```

```text
SYSERR: Required cascading foreign key pet_save_objs.pet_idnum -> pet_data.pet_data_id is missing
1) Test_pet_persistence_legacy_schema_migration_is_idempotent: unittests/CuTest/test_database_persistence.c:872: assert failed
```

Line 872 is `CuAssertTrue(tc, first_verification)`: `verify_pet_persistence_schema()` fails right after `run_pet_persistence_migrations()` succeeded. A second run on the same database fails the same way.

## What is not known yet

Whether this is only the test's fixture (it relies on something a boot leaves in the database, such as rows of `schema_migrations` or the tables' boot-time shape), or the migrations themselves leave the foreign key out when they start from the `master_schema.sql` shape. The second would matter on a fresh install whose first boot goes through the same functions, so that is the first thing to check.

## Done when

The test passes alone on a database made from `master_schema.sql`, with and without the syntax-check boot before it, and the cause is named (fixture or migration).

### Comment 3957746597

Max aka Mosheh (max757) at 2026-10-05T18:49:32.635Z.

Cause named: the test's fixture, not the migrations. In review as !24 (phase 2 of the plan, tag `object-save-fixes-p2`).

The fixture hides `pet_data`, `pet_save_objs` and `schema_migrations` behind temporary tables and records migration 2026091007 as applied, because InnoDB refuses a foreign key on a temporary table. `verify_pet_persistence_schema()` reads the key from `information_schema`, which lists the permanent tables only. The test passed only where the syntax-check boot, or the live-schema test later in the suite, had already put the key on the permanent `pet_save_objs`.

Checked with the repro above: the test alone leaves the permanent tables untouched; with the key added to the permanent table by hand and nothing else changed it passes; and `Test_pet_live_schema_cascades_objects_and_rejects_orphans` alone on a fresh `master_schema.sql` database runs all fifteen migrations on the permanent tables and verifies, so a fresh install's first boot is not affected.

The fix is in the test: it runs the pet migrations on the permanent tables before it creates the temporary ones. It then passes alone on a `master_schema.sql`-only database, with the syntax-check boot skipped and after it.
