## Description

## What happens

An object's saved special ability is rejected at load when it has no command word, which is the
normal case for an ability that fires on hit or on a critical hit.

`objsave_replace_special_ability()` (`src/obj/objsave.c`) requires eight fields:

```c
strict_sscanf(line, "%d %d %d %d %d %d %d %127s", ...) != 8
```

The writers in the same file store an empty string when the ability has no command word:

```c
"SpAb: %d %d %d %d %d %d %d %s\n", ..., (specab->command_word && *specab->command_word) ? specab->command_word : ""
```

So a record such as `SpAb: 61 30 48 0 0 0 0 ` (vampiric, level 30, on hit and on crit) has seven
fields, the load logs `SYSERR: Invalid SpAb record in object save data: 61 30 48 0 0 0 0` and the
object keeps only what its prototype gives it. An ability added to that one object (staff edit,
crafting, generated treasure) is dropped, and the next save stores the object without it.

## Since when

Commit `853a3f226` (2026-07-29, "fix residual CodeQL findings") added the field-count check. The
loader before it accepted the seven-number record and left the command word empty.

## Seen

Production log, 2026-10-04: the line above at every login of the staff character Kohdee (nine
times, same record). No other character logged it between 2026-10-02 and 2026-10-04.

## Fix

Accept seven numbers with no command word (store an empty or NULL command word, as the old loader
did), keep rejecting a record with fewer than seven numbers, and add a round-trip test in
`unittests/CuTest/test_database_persistence.c` next to the existing `SpAb: 0 0 0 0 0 0 0 cccc`
case: save an object whose ability has no command word, load it, and compare the ability.
