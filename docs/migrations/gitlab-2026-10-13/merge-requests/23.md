## What changes

- **A saved ability with no command word loads again** (`ea33ddd29`). The object writers store
  an ability as seven numbers and its command word, and the word is empty for an ability that
  fires on hit or on a critical hit. `objsave_replace_special_ability()` required eight fields,
  so the file, player and sheath loaders logged `Invalid SpAb record` and left the object with
  what its prototype gives it (nothing, for an object with no prototype), and the pet loader
  rejected the pet's whole object set. The parser now accepts seven numbers and leaves the
  command word NULL, as `parse_object()` does for a prototype's seven-field record. Fewer than
  seven numbers is still rejected.
- **The record replaces one ability, not the list** (`1d904677a`, the review finding). The
  writers store an object's first ability only, and the loader freed the whole list before it
  installed that record. While the seven-number record was rejected, a prototype-backed object
  kept its prototype's list; accepting it cut the three prototypes with two real abilities
  (#1213, #1244, #20621) to their first one at every load. The record now replaces the ability
  of its kind, or else the first one, and the rest of the list stays. A first ability that has
  a command word keeps the rest too, which it did not on master.
- **`utter` passes over an ability with no command word** (`1340e6957`, found while building).
  `process_weapon_abilities()` and `process_armor_abilities()` passed a NULL command word to
  `strcmp()`, so any uttered word crashed the server while such an object was wielded or worn.
  A prototype's seven-field record or a builder's edit could already produce that ability; the
  loader fix adds saved objects, so the guard comes first.

**Blocking: accepting the record drops every other ability of a multi-ability object**

**Location.** `objsave_replace_special_ability()`, `src/obj/objsave.c:123-142`; the writers at `objsave.c:542`, `:3499` and `:4534`.

**Defect.** The three writers store only the first ability of the list (`specab = obj->special_abilities;`, no loop). The loader frees the whole list (line 129) and installs that one record. On master a first record with no command word is rejected, so a prototype-backed object keeps the full list `read_object()` copied from its prototype. This change accepts the record, and the rest of the list is freed.

A first ability that has a command word already loses the rest on master. No multi-ability prototype in the dev world files has one first, so today nothing is truncated; after this change all of them are:

| Object | Abilities | After load |
| -- | -- | -- |
| #1213 a black longsword | Bane, Flaming Burst (`ignitus`) | Bane; `utter ignitus` does nothing |
| #1244 black scythe | Bane, Keen | Bane |
| #20621 cat-o'-nine-tails | Keen, Wounding | Keen |

Fourteen more prototypes carry two `SPECAB_NONE` placeholder records, with no effect. Every saved copy loads this way from the first login after the deploy: player rows, house rows, pet rows, sheath contents and rent files all go through this function. The row never held the other abilities, so nothing stored is destroyed, and a corrected loader brings them back from the prototype.

The description's "logged `Invalid SpAb record` and dropped the ability" is true for an object with no prototype. A prototype-backed object kept its prototype's abilities, which is why accepting the record changes more than the description says.

**Repro.** A prototype with the two records of #1244 (`3 30 48 1 20 0 0`, `15 30 1 0 0 0 0`), `read_object()`, then `test_objsave_save_obj_record()` + `objsave_parse_objects()` and `objsave_save_obj_record_db()` + `objsave_parse_objects_db()`, counting the abilities before and after. Run at `ab7a35b84` and again with `objsave.c` from `c8a28d892`, database tests on:

```
saved line: SpAb: 3 30 48 1 20 0 0
objsave.c of c8a28d892: file loader 2 -> 2, player rows 2 -> 2  (SYSERR logged, prototype list kept)
ab7a35b84:              file loader 2 -> 1, player rows 2 -> 1  (Keen gone)
```

**Fix.** Keep the list and let the record replace one ability, not all of them:

```c
  /* The writers store the first ability only. It replaces the ability of its
   * kind, or else the first one, and the rest of the list stays. */
  for (ability = obj->special_abilities; ability != NULL; ability = ability->next)
    if (ability->ability == values[0])
      break;
  if (ability == NULL)
    ability = obj->special_abilities;
  if (ability == NULL)
  {
    CREATE(ability, struct obj_special_ability, 1);
    obj->special_abilities = ability;
  }
  else if (ability->command_word != NULL)
    free(ability->command_word);
  ability->ability = values[0];
  /* level, activation_method and value[0..3] as now */
  ability->command_word = fields == 8 ? strdup(command) : NULL;
```

The `free_obj_special_abilities()` call, `ability->next = NULL` and the list assignment go. Match by kind, not by position: the first ability is not a stable place. `db.c:4151` prepends each `C` record and `genobj.c:350` writes the list in order, so an OLC save of the zone reverses the records, and a different ability is first after the next boot.

Tested on `ab7a35b84` with that change: the probe gives 2 -> 2 through both loaders, the three tests of this merge request pass, and the whole `./cutest` passes with the database tests on.

Add the probe as a test: the two-ability prototype round trip through the file loader and the player-row loader, asserting both abilities.

**Older than this merge request, still open after the fix.** The writers save one ability. A change to any other ability of an instance is not persisted (the weapon-oil upgrade loop at `act.item.c:6123` can upgrade one that is not first), and an object with no prototype keeps only its first. Saving the whole list needs one line per ability and a way to tell today's one-line rows from new ones, so it is its own work item.
