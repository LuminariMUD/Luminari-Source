the tag `object-save-fixes-p5` (`bfaaa8799`): two code commits, each with its test, a test

## Cause

A sheath's weapons hang off `sheath_primary` and `sheath_secondary`, and nothing else holds
them. Only the player save (`player_save_objs_sheathed`, rows under the owner's name) and the
`sheath` / `unsheath` commands handled them.

- `objsave_save_obj_record_db_pet()` wrote no sheath rows, and a pet has no rows under an
  owner's name anyway: a loaded sheath given to a pet came back empty when the pet was restored,
  and its weapons were in no row.
- `extract_obj()` did not look at them: junking or selling a loaded sheath, and the extraction
  after a rent save, freed the sheath and left the weapons in `object_list` with no holder.
  After a rent save their rows were written, so that was a leak only; after a junk or a sale
  they were gone from play without having been destroyed.

## What changes

`59bc44f45`: `extract_obj()` extracts what a sheath holds, beside the loop that extracts a
container's contents. Nothing nulls the pointers afterwards: the sheath is freed in the same
call. `Test_object_extraction_takes_a_sheaths_weapons` (no database) extracts a sheath holding
two weapons and finds `object_list` as it was; without the change the two weapons stay.

`2b8959cdd`: `Crash_save_pet()` writes a sheath's weapons as the pet's own objects beside the
sheath, through the pet record writer, as `House_save()` does for a house: no new table and no
migration. A worn sheath's weapons are written at `MIN(0, location)`, as inventory records,
since `pet_object_graph_valid()` refuses two records on one wear position and with them the
whole set; a carried sheath's are written at its own depth, so a sheath in a bag puts its
weapons in the bag. The restored pet carries the weapons and an empty sheath.
`Test_pet_save_stores_a_sheaths_weapons_as_its_own` (database) saves a pet with a worn sheath
holding a blade and a shield and a carried sheath holding a dagger through `pet_save_objs()`
and loads it through `pet_load_objs()`: five rows, one of them with a wear position, and the
restored pet wears an empty sheath and carries the other sheath, empty, and the three weapons.
Without the change the save writes two rows.

`4a9bd579b`: the pet test also refuses a weapon's row, the blade's and then the shield's; each
attempt fails the save, as any refused row does, and leaves the records written before it. The
first matrix run had left those two failure lines uncovered.

`docs/systems/SAVE_SYSTEMS_BREAKDOWN.md` has the pet rule, in the pets section.

The plan's check before the change held, with nothing to change: `overwrite_object()` keeps a
target's own sheath pointers (phase 7), every writer's temporary object comes from
`read_object()` or `create_obj()`, and the editors free their copies with
`free_object_strings()`, never `extract_obj()`.

**Stale sheath slot: the new traversal reads, and can extract, through freed memory**

The premise "nothing else holds them" is true, but the weapon can still leave on its own, and nothing clears the sheath's slot when it does: `do_sheath()` unequips the weapon and leaves only `sheath->sheath_primary` pointing at it, with no back-reference. Two paths extract a holder-less object:

- `delete_object()` (`src/olc/genobj.c:828-863`, from `oedit` delete at `src/olc/oedit.c:3437`) walks `object_list` and extracts every instance of the vnum, a sheathed one included.
- `point_update_object_one()` (`src/core/limits.c:2373-2405`) extracts on a timer trigger or `ITEM_DECAY`; `object_eligible()` (`src/events/point_update_periodic.c:34`) does not require a holder.

Repro (builder): a player wields a weapon and `sheath`es it. A builder opens `oedit <weapon vnum>`, deletes, confirms. The sheathed instance is freed; the sheath's slot keeps the address. The next `extract_obj(sheath)` (`junk`, a sale, `Crash_extract_objs()` at quit or rent, the holder's extraction) now runs line 3098: `extract_obj()` reads `obj->transfer_extracting` from the freed block. Every `create_obj()` / `read_object()` allocates that same 872-byte size class, so once the block is reused the flag is false on the new object and an unrelated live object is extracted and freed.

Evidence, valgrind on `bfaaa8799` with this appended to `test_database_persistence.c`:

```c
struct obj_data *sheath = create_obj(), *weapon = create_obj();
sheath->sheath_primary = weapon;
extract_obj(weapon); /* what delete_object() or the timer does */
extract_obj(sheath);
```

```
Invalid read of size 1
   at extract_obj (handler.c:3033)
   by extract_obj.part.0 (handler.c:3098)
 Address is 105 bytes inside a block of size 872 free'd
   by free (vgpreload_memcheck)
   by extract_obj(weapon)
```

Before this MR the stale slot was only read by the next player save and by `equipment`; this change makes the extraction itself follow it, which is the one path that frees.

Fix: a sheathed object knows its sheath. Add `struct obj_data *sheathed_in` to `obj_data`; set it where a slot is set (`do_sheath()`, `objsave_parse_objects_db_sheath()`), clear it where a slot is cleared (`unsheath_item()` on success, `objs_from_sheath()`), keep it in `overwrite_object()`'s kept list. Then in `extract_obj()`, before the holder removal:

```c
if (obj->sheathed_in)
{
  if (obj->sheathed_in->sheath_primary == obj)
    obj->sheathed_in->sheath_primary = NULL;
  if (obj->sheathed_in->sheath_secondary == obj)
    obj->sheathed_in->sheath_secondary = NULL;
}
```

The snippet above is the test: `object_list` back as it was, clean under valgrind.

**A sheathed artifact's destruction is invisible to the artifact ledger**

`artifact_on_extract()` (`src/obj/spec_artifacts.c:2923-2952`) runs at the top of `extract_obj()` and treats a locationless object as "a temporary prototype clone, not the live artifact instance": it returns before the mudlog, `destroy_count` and `artifact_set_owner(art, NULL)`. A sheathed object is locationless by construction (`do_sheath()` unequips it; only the sheath's slot holds it), and `artifact_of_obj()` matches by vnum (`:497`), so any wieldable artifact can be in that state.

So the destruction this MR introduces for a sheathed artifact (the sheath junked or sold, or its prototype deleted) leaves the player as owner with `instance_persisted` still true and no instance anywhere: `artifact_block_zone_load()` (`:2978`, from `src/core/db.c:5876`) then refuses the zone's copy on every reset. Junking the same weapon from inventory releases it (`:2945-2951`). Rent is already scoped by `artifact_begin_persistence_extract()` (`src/obj/objsave.c:1260`), so only the non-rent paths are affected. Before this MR the same scenario ended in the same stuck ledger through the leak, so the end state is not new, but this change is where sheathed objects start being destroyed and is the place to close it.

Fix: with the `sheathed_in` back-pointer from the other thread, `artifact_on_extract()` treats `obj->sheathed_in != NULL` as a location; it runs before the slot is cleared, and the sheath's own extraction reaches the weapon with the pointer intact. Without it, scope the two new calls as rent is scoped, a depth the early return consults.
