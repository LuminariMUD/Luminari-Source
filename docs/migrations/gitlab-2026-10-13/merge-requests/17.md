## Description

S11 of the vessel study: checked cargo trades.

Closes #10

## Problem

`cargobuy` and `cargosell` (`src/vessels/vessels_trade.c`) moved gold in memory only, then wrote
the port's supply and the cargo manifest unchecked and outside any transaction. A crash before the
captain's next routine save returned a buyer's gold with the cargo recorded aboard, or lost a
seller's gold with the cargo gone; a failed manifest write left sold cargo recorded aboard, to be
sold again after a reboot.

## Fix

The shape `a703572e3` gave freight acceptance:

- `trade_record()` writes the port's supply and the manifest in one transaction and rolls back if
  either write fails. It replaces `port_adjust_supply()`, whose UPDATE is now a prepared
  statement (`vessels_trade.c`'s formatted-SQL baseline drops from 7 to 6).
- The gold moves only after that commits, and is saved with `save_char_checked()`. If the save
  fails, the gold and the hold are restored and the pre-trade supply and manifest recorded again
  with the same helper. A refused write moves no gold.
- A sale trains the crew only once it is saved.
- If the undo cannot be recorded either (review round 1), the trade stands as recorded, in memory
  too, and the persistence service's minute save stores the gold; "undone" is said only after an
  undo commits. The crash window that remains needs a settlement record and a player-file marker:
  work item #12.

## Tests

- New DB-backed `Test_vessel_cargo_trades_record_the_gold_with_the_goods`: for each command, a
  refused manifest write and a failed character save leave the gold, the hold, the manifest rows
  and the port's supply as they were (including a whole-hold sale whose emptied lot is put back);
  a saved trade moves all four.
- The contraband test's trades now save the captain, so it uses the freight test's scratch player
  files; the three trade tests share one fixture helper for their temporary tables.

### [P2] Recover failed compensation before declaring the trade undone

**Location:** `src/vessels/vessels_trade.c:1605` (head `50ca77f2d4d2e311d8ed394b3abee1e7e2c97648`; the sale path is affected too).

If the initial trade commits, the player-file save fails (for example, because its filesystem is full or unwritable), and the compensating database write then fails (for example, after a lost database connection), this branch only logs the error and still returns with pre-trade gold/cargo and an unconditional 'trade is undone' message. The sale branch at lines 1767-1773 has the same defect. I reproduced both paths against the unchanged DB-backed test by rejecting only the compensating `START TRANSACTION`: buying 10 salt leaves the durable manifest/supply at 10/90 while memory is restored to 0 cargo and 1,000 gold; canceling a whole-hold sale leaves the durable manifest empty while memory again contains the 10 units and no sale proceeds. Subsequent quotes already use the unreverted supply, and a reload before another successful manifest write can restore unpaid purchases or discard canceled sales. Unlike the base implementation, the new compensation path explicitly restores game state after the corresponding database trade has committed. Persist a recoverable settlement/undo intent with that transaction and keep the affected ship/account pending until a checked gold save or durable compensation succeeds; retry/reconcile it before further trades or reload, and emit 'undone' only after compensation succeeds.

**Validation:** Three focused DB-backed regression tests passed. Two targeted fault-injection runs reproduced this defect, one for buying and one for selling. The injection forced the existing test's save-failure path and rejected only the compensating transaction; it did not simulate an actual simultaneous disk/network outage. Full suite and live in-game validation were not run for this review.

### [P2] Resolve an unknown COMMIT outcome before restoring trade state

**Location:** `src/vessels/vessels_trade.c:1074`, reviewed head `47a63c340b597b96abe20b0923b0f49ac8862403`.

A connection failure while receiving COMMIT's response does not establish that the transaction was rolled back. This branch nevertheless returns FALSE, so the initial-trade callers restore the old hold without moving gold; on an undo, `trade_settle()` instead restores the traded hold and keeps the moved gold. I reproduced both cases with the unchanged pinned commands and test: an independent database connection first verified the committed rows, then closing the trade connection before reading its acknowledgement produced MariaDB client error 2013 (`Lost connection to server during query`). For the initial purchase, the database held 10 units/supply 90 while the command returned with 0 units/1,000 gold; for its committed undo, the database held 0 units/supply 100 while the command reported the trade stood with 10 units/860 gold. The subsequent ROLLBACK cannot undo an already committed transaction. This creates immediate disagreement between the hold/balance and the market/manifest, so later quotes and manifest writes operate on different outcomes; it does not require the process crash tracked in work item #12. At the merge base, successfully recorded writes left the post-trade gold and hold in memory rather than reverting them on this newly checked result. Treat a lost connection during COMMIT as an unknown outcome and resolve a durable trade/undo identifier after reconnecting before selecting either state or allowing further settlement.

**Validation:** The exact-head build and three focused DB-backed regression tests passed. Two completed fault runs reproduced the initial-purchase and purchase-undo cases with actual MariaDB error 2013, independent reads of committed rows, and debugger reads of memory. The test hook induced acknowledgement loss locally and used persistent equivalents of the fixture tables in a disposable database; source and test functions were unchanged. Sale uses the same helpers but was not separately fault-injected. No full-suite, live-game, real external outage, or process-crash validation was performed.

**Reproduced.** I reproduced it on S11's logic with a real lost connection. The trade's COMMIT was
sent, and the client socket was shut down before the reply arrived (MariaDB client error 2013).
The trade tables were persistent copies in the test database. The purchase printed "The harbor
office cannot record that trade" and left 0 units and 1,000 gold in memory, while the manifest
held 10 and the supply 90. Those are your numbers.

**Fix.**

- `trade_commit()` now tells an unanswered COMMIT (any client error, 2000-2999) from one the
  server refused.
- After an unanswered COMMIT, `trade_record()` reconnects (`MYSQL_PING_CONN()`) and writes the
  same trade again. Both writes set absolute values: the port's supply, and the ship's whole
  manifest from memory. Once that second write commits, the trade (or its undo) stands whichever
  way the first COMMIT went, and memory, the manifest and the supply agree. That second commit
  resolves the outcome by itself, so no durable identifier is needed. Only this game process writes
  a ship's manifest and a port's supply, so nothing can change them between the two writes.
- Found on the way: `vessel_db_save_cargo()` kept writing after a failed write. After a lost
  connection inside a transaction, libmariadb refuses one reconnect (error 2006); the next
  statement reconnects and commits on its own. A later lot's row could therefore land outside the
  transaction. The function now stops at its first failure.

**Left for #12.** The second write can also fail, for example when the database is unreachable
just after the lost reply. The command then keeps S11's behaviour and logs that the database may
not match the hold. The next manifest write and the minute save bring the database back in line;
only a reload before then (#12's crash window) lets the database's version win. Freight acceptance
has the same COMMIT shape, but its conditional `status = OPEN` write cannot simply be repeated. I
added both cases to #12, which already covers freight and dock fees.

**Tests.** The new DB-backed `Test_vessel_cargo_trades_settle_a_commit_without_a_reply` loses
the reply for a committed purchase and for a rolled-back sale, then for the undo of each after a
failed save (one committed, one rolled back). It failed on S11's logic with only the test seam
added, and it passes now. I also ran a throwaway build with real lost connections: error 2013
after the COMMIT was sent (a purchase and an undo), and error 2006 with the connection already
gone (a sale). Memory and the database agreed in all three cases, and the second write ran on a
new session.
