## Description

Closes #12

S14 of the vessel study (`docs/ongoing-projects/vessels-ships.md`, Phase 14): a cargo trade, a
freight acceptance and a dock-fee payment are settled in two phases, so a crash between the
ship's side in MariaDB and the captain's gold in the player file no longer leaves one without
the other.

Review range: `vessels-s14-base..vessels-s14` (the S13 close-out `96b3af5a1` comes first; the
plan is `4ddf5f9ba`, the build `6bdce1e49`).

## What changes

- **Settlement row** (schema Phase 25, `vessel_settlements`). Written in the ship-side
  transaction, it carries the undo: signed deltas for the port's supply and the hold's lot, the
  contract to reopen, the dock fee owed again. Unique keys on `ship_id` and `player_id` hold a
  ship's and a player's accounts while one is open.
- **Player-file marker** (`VSet`, `GET_VESSEL_SETTLEMENT()`): the id of the newest settlement
  whose gold the file holds, saved with the gold.
- **Reconcile** (`vessel_settlements_reconcile()`), at login (from the insurance delivery every
  login makes), and as a gate at the start of `cargobuy`, `cargosell`, `contractaccept`,
  `contractdeliver`, `contractabandon` and `dockfees pay`: a row whose id is the file's marker is
  deleted; any other is undone from the row, with no gold moved. Another captain's row is judged
  from his player file, so a ship does not wait for an absent helmsman.
- **Unanswered `COMMIT`**: the row is read back with a locking read. When it cannot be read (or
  an undo cannot be recorded), the settlement is taken out of memory, the hull remembers its id,
  and her manifest is not written until a reconcile has settled it.
- `trade_settle()`'s "the trade stands and will be saved shortly" and the second write after an
  unanswered `COMMIT` are gone: the row settles both. "Undone" is said only once the undo is
  committed.

New code is in `src/vessels/vessels_settlement.c`; the commands change in `vessels_trade.c` and
`vessels_contracts.c`.

## Where to look

- `settlement_undo()` and `settlement_unresolved`: the one piece of in-memory state, and why
  `vessel_db_save_cargo()` refuses while it is set.
- "Covered" is `marker == id`, not `<=` as `VIns` and `VMer` use: with one open row per player
  the two agree, and equality does not depend on ids never restarting.
- The dock fee's undo is a restore (only when the hull owes nothing), not a delta: a runtime save
  rewrites the balance from memory at any time.

**Location.** `settlement_ship()` (this line) and `settlement_undo()` know the hull only by `ship_id`, a fleet slot. A slot can be empty in memory while its rows remain:

- boot could not rebuild her: `src/vessels/vessels_db.c:1562-1568` and `1590-1603` (`memset`, "leaving persistence intact");
- a purge that failed still frees the slot: `src/vessels/vessels_combat.c:593-600`, `src/vessels/vessels_merchants.c:499-504`, `src/vessels/vessels_ownership.c:482-487`.

**[P3] The row is deleted on a save that a host crash can still lose**

**Location.** `vessel_settlement_pay()` deletes the row as soon as `save_char_checked()` returns TRUE (this line). `save_char_checked()` (`src/player/players.c:4136-4153`) fsyncs the temporary file and renames it over the live one, and never fsyncs the directory. The rename is then durable only at the filesystem's next journal commit (ext4: up to 5 seconds by default), while the `DELETE` is durable at once (InnoDB flushes its log at commit by default).

**Repro.** Power loss, or a crash of the host or VM, inside that window after a trade. On restart the directory still names the old file (old gold, old `VSet`), the ship's side is committed, and no row is left for the reconcile to judge: a purchase keeps its cargo and its gold, and a sale loses the cargo without the gold. That is the state #12 closes, with nothing left to detect it. A crash of the server process alone, which is what the tests stop at, is not affected: the kernel already holds the rename.

**Fix.** In `save_char_checked()`, after `rename()`, open the file's directory and `fsync()` it, so the row is deleted only once the file that names it cannot be lost. A failure of that fsync should be logged and not returned: the new file is in place by then, and a FALSE would send the undo against a file that already holds the gold (the invariant the record states for a failed save). Every other caller of the checked save gets the same guarantee.
