## Decisions

- Price by the arm a rank adds: the third arm 9 RP, the fourth 6 RP, each arm past four 1 RP.
  The split of Four Arms' 15 follows what each arm opens: the worn positions three to one (the
  lost-slot row the other way), and the weapon hands by their swings in `plan_second_pair()`,
  five candidates to four at level 30 with haste, the fourth hand's last three behind the
  two-weapon feats, so the 11 RP of weapon hands split 6 to 5.
- Mixed sources: a race is priced by the arm count it ends with, whatever mix of Four Arms,
  Extra Arms ranks and `arm_adjust` produces it, since `arm_count()` is the only count the game
  reads. A negative `arm_adjust` is a drawback by the lost-slot row (one arm or none: the cap).
- The single-trait cap exemption stays Thri-Kreen's Four Arms alone (composition rule 2). A
  third arm is over the cap in every tier but Epic quest, and four arms fit only there, so
  another race taking arms records its own exemption in that rule.
- The monk's empty third hand is the swing a weapon there makes: `plan_second_pair()` plans one
  third-hand chain, set by either, and gives the monk no candidate of its own; the fourth hand
  always needs a weapon. Class interaction, which the model does not price, so it is inside the
  15 RP and Thri-Kreen stays at 20.0 RP.

Max aka Mosheh (max757) at 2026-10-08T07:31:58.225Z. System event: no. Resolved: True.

Review location: docs/ongoing-projects/object-save-fixes-and-arm-pricing.md; old line None; new line 754; head e6c85bf50d552d2a58e12a645d74908d50ad1467.

**The recorded audit recipe misses CR-terminated `A` records and two-field affect lines, and the DB query cannot see prototype-granted feats**

Location: this recipe paragraph, and the world-object row of the audit table above it.

Repro on the dev copy (this worktree):

```
grep -rl $'\r' lib/world/obj              # 73.obj 321.obj 296.obj
grep -c $'^A\r$' lib/world/obj/296.obj    # 70  (73.obj: 1, 321.obj: 1)
```

`get_line()` (`src/core/utils.c:3746`) strips a trailing `\r`, so the game loads all 72 of those affects; `grep -rn -A1 "^A$"` never prints them. None of the 72 has location 49 today, so the 33 stands on dev, but the recipe written down for the next audit is blind to every `A` record in those three files (and to any file that acquires CR line ends later), and "33, the same on both sides" is not a count over all `A` records.

Second gap: `parse_object()` accepts two-field `A` lines (`src/core/db.c:4058`, `retval == 2`; 4 such lines on dev, in `1074.obj` and `20830.obj`). `"-49 132[01] "` needs a trailing space, so a two-field `49 1320` line is missed.

Third gap: `objsave_save_obj_record_db()` writes an `Aff :` line only when the affect differs from the prototype (`diff`, `src/obj/objsave.c:486-497`). A saved copy of a prototype that grants 1320 carries no `Aff :` line, so `WHERE serialized_obj REGEXP 'Aff : [0-9]+ 49 132[01] '` finds OLC, treasure and crafting edits only. That holds as long as the world grep runs first and on the world files production loads; the recipe presents the query as "a saved object's affects", which it is not.

Fix:

```
grep -rn -A1 $'^A\r\?$' lib/world/obj | tr -d '\r' | grep -E -- '-49 132[01]( |$)'
```

plus one sentence: a prototype's own affects never appear in `serialized_obj`, so the world grep is the only check for them.

**Two-field lines**: reproduced on both sides, the same four (`1074.obj` lines 10, 12, 14 and `20830.obj`, all `1 1` or `17 1`), none at location 49. The recipe now ends the feat with `( |$)`.

**Prototype affects**: confirmed in `objsave_save_obj_record_db()`, the `diff` test. The recipe now says a prototype's own affects never reach `serialized_obj`, so the world grep, on the files production loads, is the only check for them.

**CR-terminated `A` records**: none exist, on either side. Each of `73.obj`, `321.obj` and `296.obj` holds exactly one CRLF line, a room description, and no `A\r` header (Python, `d.count(b"\nA\r\n")` is 0 over all 769 files on both hosts; GNU grep `-c -E '^A[[:cntrl:]]$'` is 0 on production). The 70 / 1 / 1 came from the development `grep`, which is ugrep 7.8.4: it breaks a pattern at a CR, so `$'^A\r$'` counted something else (`^A` alone matches 10 lines of `296.obj`). The gap in the recorded recipe is still real, since `get_line()` strips a trailing CR and GNU grep's `^A$` would not match such a header, so the recipe takes it.

**The proposed command does not work where the audit runs.** Bash decodes `\?` inside `$'...'` to a plain `?`, so `$'^A\r\?$'` is the pattern `^A<CR>?$`, and under GNU grep 3.11 on production it matches nothing: run there, it gave 0 against the old recipe's 33. Under ugrep it happens to work, for the wrong reason. The recorded form is

```
grep -rn -A1 -E '^A[[:cntrl:]]?$' lib/world/obj | tr -d '\r' | grep -E -- '-49 132[01]( |$)'
```

which gives 33 location-49 records on both hosts (GNU grep and ugrep) and none for 1320 or 1321, so the table's 33 is now the count the recipe makes. The record notes why the class rather than a CR in the pattern.
