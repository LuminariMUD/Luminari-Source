## Cause

It is the test's fixture, not the migrations.

`create_legacy_pet_temporary_schema()` hides `pet_data`, `pet_save_objs` and `schema_migrations`
behind temporary tables and records migration 2026091007 as applied, because InnoDB refuses a
foreign key on a temporary table. `verify_pet_persistence_schema()` reads the key from
`information_schema`, which lists the permanent tables only. So
`Test_pet_persistence_legacy_schema_migration_is_idempotent` passed only on a database where
something had already put the key on the permanent `pet_save_objs`: the syntax-check boot, or
`Test_pet_live_schema_cascades_objects_and_rejects_orphans`, which runs after it in the suite.

Checked on a database built from `sql/master_schema.sql` alone, boot skipped:

- The test alone fails with one error, the missing foreign key, and leaves the permanent tables
  untouched: no key, no pet migration recorded.
- With the key added to the permanent table by hand and nothing else changed, it passes.
- The live-schema test alone runs all fifteen migrations on the permanent tables from the
  `master_schema.sql` shape; 2026091007 adds the key and the schema verifies. A fresh install's
  first boot goes through the same functions and is not affected.

**Finding 1 (data loss on a failure path): when the new permanent-table migration fails, the test overwrites `owner_id` on every permanent `pet_data` row**

**Location.** `unittests/CuTest/test_database_persistence.c:832-845` at `115b6d846`.

`fixture_created = live_tables_migrated && create_legacy_pet_temporary_schema(connection)` skips the temporary tables whenever the new first call returns false. Nothing below it stops. Line 842 runs `UPDATE pet_data SET owner_id = 4294967295` with no `WHERE` and no guard, and with no temporary `pet_data` in the session that name is the permanent table.

On base the statement could reach the permanent table only if a `CREATE TEMPORARY TABLE` failed. This MR puts in front of it a run of up to fifteen DDL statements on shared tables that fails in ordinary states; the description itself names one.

**Effect.** Every row of the configured database's `pet_data` ends with `owner_id = 4294967295`. `prepare_saved_pet_row()` (`src/player/players.c:7245`) refuses a row whose `owner_id` is neither 0 nor the owner's, and the pet queries at `players.c:7110`, `:7775`, `:7823` and `:7877` filter on the same pair, so no owner loads or reclaims those pets again. CI's disposable databases hold no pet rows, so nothing is lost there; the loss is on any database that does hold them. The sibling `Test_pet_live_schema_cascades_objects_and_rejects_orphans` keeps its row writes in a transaction it rolls back; this test now has no such protection.

**Repro.** mariadb:10.11, database built from `sql/master_schema.sql`, boot skipped, one pet row inserted with `owner_id = 7`. Three states that make the first call fail, each run on base `8c0c5bd16` and on head:

| State | Base | Head |
| -- | -- | -- |
| Key added to the permanent `pet_save_objs` by hand, nothing recorded (the plan's step 1 probe state) | passes; row keeps `owner_id` 7 | fails at `:873`, `Failed to apply migration 2026080503: Cannot change column 'pet_idnum': used in a foreign key constraint`; row has 4294967295 |
| Fully migrated database, test user granted only SELECT, INSERT, UPDATE, DELETE, CREATE TEMPORARY TABLES | fails at `:872`; row keeps 7 | fails at `:873`, `CREATE command denied ... schema_migrations`; row has 4294967295 |
| Two `./cutest` processes started together on one fresh database | not applicable, the test was session-private | 3 of 3 rounds: one process fails with `Failed to record migration 2026080501: Duplicate entry`; row has 4294967295 |

Most pet persistence tests also isolate themselves with temporary tables. Two
