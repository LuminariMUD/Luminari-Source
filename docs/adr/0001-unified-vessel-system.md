# 1. Unified Vessel System Architecture

**Status:** Accepted
**Decision date:** 2025-12-29
**Last reviewed:** 2026-07-29

## Context

LuminariMUD had three vessel implementations derived from CWG, Outcast, and
Greyhawk. They overlapped in purpose but used different commands, navigation
models, persistence assumptions, and maintenance paths. The wilderness system
already provided the world coordinate, terrain, elevation, weather, path, and
region models, but vessels did not use it as a complete navigation substrate.

Maintaining separate vessel worlds would multiply fixes, make content
campaign-specific in core C, and prevent vessels from interacting consistently
with land players and other wilderness systems.

## Decision

Maintain one transport system with two tiers:

1. Use the Greyhawk ship model as the heavy vessel foundation.
2. Consolidate vessel behavior in the `vessels*.c` modules.
3. Use a lightweight vehicle tier for carts, wagons, mounts, and carriages.
4. Expose a unified transport command layer where vessel and vehicle behavior
   overlaps.
5. Generate multi-room vessel interiors from builder-authored prototypes and
   room templates.
6. Persist vessel identity, interiors, ownership, crew, cargo, automation, and
   gameplay state in MariaDB.
7. Provide waypoint, route, schedule, autopilot, and NPC-pilot automation.

### Wilderness integration invariants

The unified system has no private geography:

- A vessel position is a wilderness coordinate backed by the shared dynamic-room
  pool.
- Traversal reads the sector generated by wilderness terrain and region rules.
- Draft, grounding, and submarine limits read wilderness bathymetry.
- Speed, visibility, and hazards read the shared wilderness weather field.
- Roads and rivers are wilderness paths.
- Named seas, legal waters, encounter areas, trade lanes, and special waters are
  builder-authored wilderness regions.
- Altitude and depth extend the same `(x, y)` wilderness column rather than
  creating another map.

When a vessel feature needs an environmental signal that wilderness does not
provide, extend the wilderness system and consume the shared result.

### Content and operations invariants

- Core C remains campaign-neutral; setting-specific names and encounters live in
  world or database content.
- Tunable gameplay values are data-driven.
- Builder workflows use OLC, wilderness region tooling, and DG scripts.
- The dynamic-room pool is shared infrastructure and must be monitored and
  protected from exhaustion.
- The vessel-system configuration toggle gates gameplay and builder command
  dispatch plus both vessel tick groups. Diagnosis and recovery commands remain
  available while the subsystem is stopped.

## Consequences

### Positive

- One code path owns vessel fixes, testing, persistence, and player commands.
- Ships, vehicles, walkers, weather, regions, and encounters share a coherent
  world model.
- Free navigation supports exploration, trade, combat, and emergent content.
- Builders can create hulls, interiors, routes, ports, and encounter content
  without recompiling.
- The architecture supports a 500-vessel ceiling with acceptable memory use:
  the measured base ship structure is 4,744 bytes, or about 2.3 MB for 500
  vessels.
- Existing D20, PvP, DG-script, OLC, protocol, and persistence systems remain
  authoritative instead of being reimplemented.

### Negative

- Legacy content must be migrated to the unified identity and command model.
- A broad feature set increases live-tick, lifecycle, and schema complexity.
- Ships compete with walkers and other systems for wilderness dynamic rooms.
- MariaDB is required for the complete persistence and content model.
- Vessel identity crosses fleet slots, object values, persistent rows, and room
  pointers. The fleet slot is canonical; every boundary must validate rather
  than infer identity from occupancy or naming conventions.

## Alternatives Considered

### Maintain all three vessel systems

This avoided initial migration but retained three maintenance paths and
inconsistent player behavior. It was rejected as unsustainable.

### Use predefined port-to-port tracks

This reduced navigation complexity but prevented free wilderness exploration and
made environmental systems largely cosmetic. It was rejected as too restrictive.

### Create a vessel-only map or physics model

This could have supported specialized naval simulation but would duplicate
terrain, weather, coordinates, and content tooling. It was rejected in favor of
one shared world.

### Require client-side rendering

This could provide richer maps but would make core play depend on a particular
client. Optional protocol state is supported; the text interface remains
complete.

## Validation

The decision remains valid when:

- Vessel behavior uses shared wilderness data rather than coordinate literals or
  private environmental tables.
- The production-linked integration suite and manual vessel regression pass.
- Persistence survives reboot, copyover, sinking, transfer, and deletion.
- The complete subsystem stays within its live tick and dynamic-room budgets.
- Operators can disable and recover the system safely.
